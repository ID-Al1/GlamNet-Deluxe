# Bonisa — full package brief for Replit

## How to use this

This is the single source of truth for restyling the existing GlamNet/Bonisa app on Replit. It merges three things into one document: the visual redesign brief, the approved home-screen mockup (`bonisa_home.html`), and the current state of the codebase, including behavior that was recently fixed and must not be regressed.

It is a **skin change plus the specific behaviors listed in section 10**. Do not rebuild the app.

---

## 1. Rules of engagement (read first)

**Do not change:**
- Any existing feature, screen, route, database field, API call, auth flow or booking logic
- Any real data, seeded data or placeholder data already in the project
- The number of screens or the navigation structure
- Any component's behaviour, state or props — especially the behaviors in section 10, which were deliberate fixes

**Only change:**
- Colours, fonts, spacing, corner radii, shadows, borders
- The logo mark and wordmark
- Icons (replace every emoji with a proper line icon)
- The greeting block on the home screen
- Where and how photography appears

**Names:** replace every instance of `GlamNet` with `Bonisa` in UI text, page titles, meta tags, alt text and the manifest. Leave variable names, file names, folder names, package names and database keys alone unless they break the build.

**No invented content.** The mockup (`bonisa_home.html`) shows sample salons, prices, distances and names purely to illustrate layout — none of that text ships. Every slot is a container filled from data that already exists in the app. If a data source does not exist yet, hide the section entirely (label included). Never render a made-up value, a permanent skeleton loader, or filler.

**Payments:** the payment provider is **undecided**. Never reference PayFast or any specific provider anywhere — UI, comments, or docs. The confirm step says only "Payment processed securely."

---

## 2. What the app is

Bonisa is a South African marketplace connecting beauty professionals (makeup, hair, nails, barbering) with clients who book them directly, and with brands who hire several artists at once for campaigns. Tagline: **Reveal Your Beauty**.

Three apps in one codebase, one login, three totally separate job screens:

- **Client** (`/client`) — "I need to look amazing." Browse artists, book a slot, pay. **Direct booking only. No applying, ever.**
- **Artist** (`/artist`) — "I need work." See requests, accept/decline, track earnings. Earnings always shown **net of the 18% commission** — the number that lands in their pocket, never gross.
- **Brand** (`/brand`) — "I need talent." Post a campaign, review applicants, confirm. **Applying exists only here.**

If an "apply" button is ever being built in the Client app, stop — wrong app.

### Routes (do not add or remove)

```
/                              RoleGate → Onboarding (no saved role) or Splash → dashboard (saved role)
/client                        Client home — dashboard, browse, search
/client/artist/:id             Artist profile
/client/artist/:id/book        Booking flow (3 steps)
/client/confirmation           Booking confirmation
/artist                        Artist dashboard
/artist/requests               Booking requests
/brand                         Brand dashboard
/brand/create                  Create campaign
/brand/campaign/:id/applicants Applicant review
*                              Redirect to /
```

## 3. Design tokens

Define once in the global stylesheet or theme file, reference everywhere. No hardcoded colours in components — this rule has been broken before (a form kept old-brand hex values after a restyle) and it's the first thing to audit.

```
--plum:        #6D1F36   primary, buttons, active states
--plum-light:  #8E3C56   logo petal, secondary accents
--plum-dark:   #591A2C   logo petal, hero gradient
--cream:       #FDF8F0   page background
--ink:         #231519   all text
--gold:        #C1793A   ratings, notification dot, small highlights, logo centre ring
--line:        #EFE3D3   borders and dividers
--surface:     #FFFFFF   cards on top of cream
--sage:        #7C8B6F   confirmed / success states only
```

Text colour is always `--ink`, varied by opacity: 100% headings, 60% body, 45% captions, 40% section labels.

**The accent rule:** one or two plum touches per screen max. A screen full of plum has no focal point.

**Type**
- Display: Playfair Display, weights 500 and 600. Only for: logo wordmark, the user's name in the greeting, hero headlines, artist names, large numbers, and the confirmation screen's italic artist signature.
- Body and UI: Inter, weights 400, 500, 600. Everything else.
- Never Playfair on buttons, labels, form fields or body copy.

Scale: 29px greeting name / 25px hero headline / 13.5px card titles / 12.5px buttons / 11px meta text / 10px uppercase section labels with 1.5px letter spacing.

**Shape**
- Cards and list rows: 20px radius, 1px `--line` border, white fill
- Images and thumbnails: 15–22px radius
- Buttons and chips: 999px pills, 11px small rectangular buttons
- Shadows: `0 2px 10px rgba(109,31,54,0.04)` only. No hard drop shadows anywhere.

Spacing: 20px screen padding, 26px between major sections, 11px between stacked cards. Max content width `max-w-lg`, centred.

**Wordmark:** "Bonisa" in Playfair Display 600, 19px, 9px right of the mark, vertically centred.

**Rules:** mark + wordmark in the app bar and splash. Mark alone for favicon, app icon, anything under 24px. On a plum background swap the centre circle fill to `--cream`, petals unchanged. Respect `prefers-reduced-motion`: show the static mark instantly.

## 5. Greeting (French — non-negotiable)

Two lines, top of the client home screen, above everything else. The same French greeting also appears on the Splash and Onboarding screens paired with the wordmark ("Bonjour, Bonisa").

Line one changes with device local time:

| Local time | Greeting |
|---|---|
| 00:00–11:59 | `Bonjour,` |
| 12:00–17:59 | `Bon après-midi,` |
| 18:00–23:59 | `Bonsoir,` |

13px, `--ink` at 45% opacity, sentence case, comma included. Keep accents exactly as written (`après`), page must be UTF-8. Never translate to English or any other language, never add a fourth variant. **No English "Good morning/afternoon/evening" anywhere in the product.**

Line two: the signed-in user's **first name only**, Playfair 600, 29px. No name on file → show line one alone. Never print a placeholder name.

### Launch sequence (already built — preserve it)

App open with a saved role: Splash screen → logo blooms open → French greeting fades in right after (~0.95s delay) → auto-navigate to that role's dashboard at ~2.2s. No tap required. First-time visitors (no saved role) get the Onboarding role picker instead, with the same bloom + greeting, then the wordmark, question, role cards and Continue button fading up in sequence after the bloom.

## 7. Realism rules

The app must feel like a real product in a real city, not a template.

- **South African number formatting everywhere:** prices as `R680` and `R1 200` (space thousands separator, no cents), ratings with a decimal comma (`4,9`), distances as `2,4 km`, 24-hour times (`16:00`) in list metadata. Keep the booking flow's existing 12-hour slot display (`11:00 AM`) as is — do not churn it.
- **Ratings always carry review counts** — `4,9 (212)` reads real; a bare `4,9` reads fake. Both values come from existing data.
- **Availability is specific, not generic:** "Today 16:00" beats "Available now" wherever a real next-slot value exists in data; fall back to the existing available/booked-today dot otherwise.
- **Response-time stats stay:** "responds in ~10 min" on client-facing cards, and the artist dashboard's response-time nudge ("Fast responders get booked 3× more often") are product differentiators, not decoration. Keep them.
- **Photography is the main visual material.** Where photos appear: hero, look cards, provider thumbnails, artist profile header, portfolios. Where they never appear: behind body text, inside buttons, as page backgrounds, as filler in empty sections. Subject matter: real beauty work and the people wearing it — braids, locs, nails, lashes, makeup, close crops of finished results, portraits cropped so the look is the subject. Warm natural light, skin tones that reflect the actual user base. Always `object-fit: cover`. Photo carrying text gets the plum veil first. No filters, no black and white, no heavy vignettes.
- **Missing image = branded fallback, not stock:** a `--line` coloured block with the logo mark centred at 20% opacity (the existing `BeautyImage` component already does gradient fallback + fade-in on load — keep that behavior, restyle the fallback to this spec).
- **Motion is quiet and purposeful:** content fades up on load (~0.5s ease-out), list cards stagger by ~60ms, images fade in when loaded rather than popping. Nothing loops, nothing bounces. Respect `prefers-reduced-motion` on everything.
- **Nothing pretends to work.** Controls without a built destination render visibly disabled (40% opacity, `disabled`, "Coming soon" title) — never tappable-looking and silently dead. Currently that's: Bookings/Messages/Profile tabs, the artist profile's message and "more" buttons. The tab bar's five labels are Home, Search, Bookings, Messages, Profile (Search focuses the home search field).

## 10. Existing behaviors that must survive the restyle

These were deliberate fixes. Regressing any of them is a bug:

1. **Booking persistence:** completing a booking saves it (localStorage until the API exists) and the client home's "Next appointment" card shows that real booking in preference to seeded data. A user's booking never vanishes after confirming.
2. **Session version gate:** the stored role is version-gated; bumping the version constant forces every returning visitor through onboarding once (used for the GlamNet→Bonisa cutover). Keep the mechanism.
3. **Deep-link booking:** every Book button that names a service (home recommendation card, artist profile service rows) opens the booking flow with that service preselected, landing on date/time — never a bare profile link labelled "Book".
4. **Category/filter sync:** the browse categories and the filter chips derive from one shared list. No category may exist that has zero matching providers and no filter.
5. **Honest disabled controls:** anything without a real destination renders disabled with "Coming soon" (see section 7). Don't wire them to wrong destinations; don't make them look alive.
6. **Notification bell:** opens a real dropdown fed by existing notification data, with unread markers; the gold dot appears only when unread items exist.
7. **Saved artists:** the heart on an artist profile is a real persisted toggle (filled plum when saved).
8. **Image fallback:** photos fade in on load; a failed or missing image shows the branded fallback, never a broken-image icon.
9. **French greetings only** — including the home dashboard's greeting. No English time-of-day greeting anywhere.
10. **Net earnings:** artists see earnings after the 18% commission, labelled as such, never gross.

12. Production Marketplace Architecture (Critical Addition)

This section extends the existing specification.

It does not replace any previous requirement.

If any requirement in this section conflicts with an earlier section, this section takes precedence.

⸻

Payment Philosophy

Bonisa is a managed marketplace.

The platform is responsible for safely holding client funds until services have been successfully delivered.

Payments are never transferred directly from client to artist.

Every completed booking follows an escrow workflow.

The implementation must be designed so the underlying payment provider can be changed later without changing the product behaviour.

No payment provider names should appear anywhere in the UI.

⸻

Escrow Payment Model

When the client pays for a booking:

The booking amount is immediately divided internally into two balances.

Artist Allocation

82%

Platform Allocation

18%

These balances are accounting values only.

Neither balance is released immediately.

Both remain inside platform escrow until the booking has been validated.

⸻

Booking Lifecycle

Every booking must move through the following states.

Draft

↓

Awaiting Payment

↓

Confirmed

↓

Upcoming

↓

In Progress

↓

Awaiting Completion Confirmation

↓

Completed

or

Payment On Hold

or

Cancelled

⸻

Appointment Completion

At the scheduled appointment time the booking automatically enters

Awaiting Completion Confirmation

Both parties are independently asked to confirm.

Client

Question

“Did you receive your appointment?”

Actions

• Yes, everything went well

• Report a problem

Artist

Question

“Did you complete this appointment?”

Actions

• Yes, appointment completed

• Report an issue

Neither party can see the other’s response before submitting their own.

⸻

Automatic Escrow Release

If BOTH confirmations are positive:

Booking Status

Completed

Immediately perform:

• Release 82% to artist

• Release 18% to Bonisa

• Record permanent payment transaction

• Update artist earnings dashboard

• Lock booking from further edits

• Mark appointment complete

This should happen automatically.

No administrator intervention.

⸻

Dispute Protection

If confirmations do not match

OR

either party reports an issue

OR

only one side confirms

then:

Booking Status

Payment On Hold

Funds remain inside escrow.

Nothing is paid.

The system automatically creates a dispute.

If only one side confirms:

Display

Waiting for the other party.

Continue reminding the other user.

After the configured timeout (default 48 hours):

Escalate for manual review.

The timeout must be configurable.
